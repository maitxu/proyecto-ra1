01 Aplicación hipotética

Matriculator

Problema y objetivo

CEBANC quiere llevar un control de accesos al parking del centro, para lo que se crea esta propuesta para poder tener registros de entradas, salidas... para poder utilizar después para tomar decisiones.
La propuesta permite analizar qué lenguajes y tecnologías serían adecuados para una solución de visión artificial sin necesidad de implementar ni entrenar el modelo en este trabajo.

📷
EntradaImágenes de prueba de vehículos, preferiblemente sintéticas, anónimas o abiertas.
🧠
ProcesamientoValidación de imagen → preprocesado → detección de la matrícula → posible OCR → validación.
🔎
SalidaRegión detectada, texto de matrícula cuando proceda y nivel de confianza.
👤
Revisión humanaUn resultado de baja confianza debe quedar sujeto a comprobación antes de utilizarse.

Lenguaje principal de la aplicaciónJS

Seleccionamos Python como lenguaje unificado para la aplicación general y el componente de IA.

Lenguaje principal para IAPython

La elección se apoya en su ecosistema de IA y datos: PyTorch, TensorFlow, Pandas....

Descarte razonado

  • R: excelente para estadística y exploración, pero se considera menos adecuado para pipelines de inferencia y despliegue web en tiempo real.
  • C++: ofrece máximo rendimiento, pero con mayor coste de desarrollo y complejidad de gestión de memoria; se reserva como posible motor subyacente.
  • PHP: destaca en backend web, pero la documentación del equipo lo descarta para la capa de IA por su ecosistema mucho menor de ML/deep learning.
  • Java: aporta solidez empresarial, pero el equipo prioriza la agilidad y el ecosistema de modelos preentrenados de Python.
03 Arquitectura

Cómo funcionaría Matriculator

Flujo general, preparación de datos y proceso para detección de matrículas.

Flujo general · 9 etapas

El flujo comienza con la llegada del vehículo y termina mostrando el resultado. La revisión humana aparece cuando la matrícula no se puede resolver con suficiente seguridad o los datos del vehículo son dudosos, en ese caso habrá alguien en la garita para realizar las comprobaciones o registros pertinentes.

01Llegada del vehículoSe detecta un coche esperando en la barrera.
02Foto de la matrículaLa cámara captura la matrícula y envía la imagen.
03Lectura con IALa IA localiza la matrícula, lee caracteres y aporta confianza.
04ComprobaciónSi la lectura no es clara, pasa a revisión humana.
05Búsqueda en BDSe comprueba propietario, tipo de usuario y permiso.
06Comprobación del permisoSe autoriza, deniega o deriva a revisión.
07Revisión en garitaUna persona decide los casos no resueltos automáticamente.
08Apertura / cierreLa barrera se abre si el acceso está autorizado.
09Fin y registroSe guarda foto, fecha, hora y resultado; después puede registrarse la salida.

Después de integrar el modelo

Cuando el modelo ya está disponible, el flujo operativo documentado es el siguiente:

1
Recibir imagenLa cámara envía la fotografía de la matrícula.
2
Obtener matrículaLa IA intenta localizar y leer la matrícula y devuelve una confianza.
3
Control de errorSi no hay foto, no se reconoce la matrícula o la confianza es insuficiente, se solicita revisión.
4
Consultar base de datosSe comprueba el vehículo, sus datos y su permiso.
5
Decidir accesoDocente o vehículo con permiso: autorización; registrado sin permiso: denegación; datos dudosos: garita.
6
Barrera y registroSe abre o se mantiene cerrada y se guarda el resultado con fecha y hora.
7
Registrar salidaAl salir, se busca la entrada pendiente y se guarda la fecha y hora de salida.

Pseudocódigo

def obtener_matricula():
    foto = hacer_foto_con_camara()
    if foto is None:
        return foto, None, "La cámara no ha enviado ninguna foto"
    matricula, confianza = leer_matricula_con_ia(foto)
    if matricula is None or confianza < 0.80:
        return foto, None, "No se distingue bien la matrícula"
    return foto, matricula, None
def decidir_acceso(matricula, problema):
    if problema is not None:
        return pedir_revision_en_garita(problema)
    vehiculo = buscar_vehiculo(matricula)
    if vehiculo is None:
        return pedir_revision_en_garita("No conocemos este vehículo")
    if vehiculo.datos_incompletos:
        return pedir_revision_en_garita("Hay datos que revisar")
    if vehiculo.tipo == "docente" or vehiculo.tiene_permiso:
        return "Autorizado automáticamente"
    return "Denegado: no tiene permiso"
def procesar_acceso():
    foto, matricula, problema = obtener_matricula()
    resultado = decidir_acceso(matricula, problema)
    fecha_entrada = None
    if resultado in ["Autorizado automáticamente", "Autorizado manualmente"]:
        abrir_barrera()
        fecha_entrada = obtener_fecha_y_hora()
    else:
        mantener_barrera_cerrada()
    guardar_intento(foto, matricula, resultado, fecha_entrada)
    mostrar_resultado(resultado)
    return resultado
def registrar_salida(matricula):
    entrada = buscar_entrada_sin_salida(matricula)
    if entrada is None:
        return "No encontramos una entrada pendiente de salida"
    entrada.fecha_salida = obtener_fecha_y_hora()
    guardar_cambios(entrada)
    return "Salida registrada"

05 Preguntas adicionales

Conclusiones

¿IA débil o IA fuerte?

La propuesta se aproxima a una IA débil o especializada: resuelve una tarea concreta, la lectura de matrículas, y no pretende tener capacidades generales. Además, la decisión de acceso puede requerir revisión humana cuando hay dudas sobre la lectura o los datos.

¿Modelo preentrenado o desde cero?

En este sentido creemos que es mejor "aprovechar" modelos existentes o preentrenados y adaptarlos al caso. La razón es reducir tiempo y coste y aprovechar un ecosistema más seguro que el que podríamos crear de 0.
